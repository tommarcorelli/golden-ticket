En se faisant passer pour un contrôleur (`mimikatz lsadump::dcsync`), il réplique le hash NTLM d'un Domain Admin sans jamais être admin ni toucher au compte cible, puis le rejoue en Pass-the-Hash. Le twist pédagogique : la faille est un droit **posé sur l'objet domaine** (pas sur un compte, `get-objectacl domain`), et c'est le chemin réel par lequel on obtient le hash krbtgt d'un Golden Ticket — ça referme la boucle avec le Chapitre Final, où DCSync n'apparaissait que déjà-Domain-Admin. Complète le trio « droit étroit mais mortel » avec les Scénarios 03 (ACL) et 06 (Shadow Credentials). - [x] **Scénario 08 — Délégation sans contrainte + coercition (PetitPotam)** : le joueur contrôle `svc_web`, simple administrateur local du serveur applicatif `WEB01` — **aucun droit sur le domaine** au départ. `WEB01` a été laissé en délégation sans contrainte (`get-domaincomputer -unconstrained` le révèle, à côté du contrôleur de domaine `DC01` pour qui c'est normal). Le joueur force `DC01` à s'authentifier sur `WEB01` via `petitpotam`, ce qui met en cache le TGT complet du compte machine `DC01$` ; il l'exporte (`mimikatz sekurlsa::tickets /export`), l'injecte (`mimikatz kerberos::ptt`) pour devenir littéralement `DC01$` aux yeux de l'annuaire, puis réplique le hash de `krbtgt` (`mimikatz lsadump::dcsync`) — la clé de tous les tickets du domaine. Le twist pédagogique : referme la chaîne complète « accès admin local anodin → délégation mal configurée → coercition → capture de ticket → Pass-the-Ticket → DCSync », sans jamais toucher un mot de passe ni posséder de droit de domaine au départ ; complète le trio de chemins DCSync avec le Scénario 07 (droits de réplication délégués directement) en montrant une deuxième voie, via la délégation Kerberos plutôt que via des droits LDAP. Ajouté hors-roadmap le 20 juillet 2026 (`SCENARIOS.unconstrained` dans `js/scenarios.js`), sur le même moteur générique — aucune modification du moteur nécessaire (nouvelles règles `NOISE` pour `petitpotam`/`sekurlsa::tickets`/`kerberos::ptt`). - [x] **Scénario 10 — Abus de GPO (délégation copiée sur le mauvais objet)** : le joueur contrôle `t.giraud`, technicien helpdesk délégué de longue date pour éditer une GPO d'impression — un droit légitime et volontairement restreint. Ce même droit d'édition (`Edit settings, delete, modify security`) se retrouve, copié « par commodité », sur une seconde GPO liée à l'OU des serveurs applicatifs (`get-domaingpo` révèle les deux GPO et leurs liaisons, `get-objectacl <gpo>` révèle laquelle est anormale). Le joueur peut abuser des **deux** GPO de façon identique via `gpoabuse -gpo <nom> -type localadmin -target <compte>` (réglage Restricted Groups), mais une seule mène quelque part : celle liée à `SRV-APP03`, où un Domain Admin (`m.faure`) se connecte régulièrement pour de la maintenance. Une fois admin local via `gpupdate /force /target:SRV-APP03`, `mimikatz sekurlsa::logonpasswords` récupère son hash NTLM en cache, rejoué en Pass-the-Hash (`pth /target:DC01 /user:m.faure /hash:<hash>`) jusqu'à une session Domain Admin. Le twist pédagogique : les deux GPO acceptent le même abus technique — c'est la lecture des indices (quels postes sont réellement liés à quelle GPO, qui s'y connecte) qui distingue une impasse d'un chemin réel, pas la répétition mécanique de la commande ; et une seule case cochée en trop lors d'une délégation peut livrer l'administration locale de tout un parc de serveurs. Ajouté le 23 juillet 2026 (`SCENARIOS.gpo` dans `js/scenarios.js`), sur le même moteur générique — aucune modification du moteur nécessaire (nouvelles règles `NOISE` pour `get-domaingpo`/`gpoabuse`/`gpupdate`). Glossaire enrichi (entrées « GPO (Group Policy Object) » et « Restricted Groups »).

- [x] **Chapitre Final II — Le Pont Hybride (Azure AD Connect, dual-royaume)** : nouveau chapitre épique (`SCENARIOS.hybridbridge`, `epic:true`, deuxième bannière dédiée sur l'accueil avec sa propre variante visuelle bleu/cyan). Le joueur part administrateur local de `SRV-ADCONNECT01`, le serveur qui héberge Azure AD Connect. `dump-adsyncdb` puis `decrypt-adsynccreds` extraient et déchiffrent (via les clés DPAPI locales de la machine) les identifiants de **deux connecteurs distincts** : le connecteur on-prem (`svc_adsync`, droits de réplication délégués) et le connecteur cloud (compte à privilèges Entra ID). Le joueur bascule sur le connecteur on-prem pour DCSync krbtgt et forger un Golden Ticket (royaume on-prem conquis), **puis** s'authentifie séparément avec le connecteur cloud pour devenir Global Administrator du tenant (royaume cloud conquis) — le flag final n'est accessible qu'en ayant conquis les deux. Le twist pédagogique, distinct du premier Chapitre Final : ce n'est pas un enchaînement de trois techniques indépendantes, mais **un seul pivot (un serveur) qui ouvre deux royaumes simultanément** — la vraie raison pour laquelle Azure AD Connect doit être traité comme un actif Tier 0 au même titre qu'un contrôleur de domaine. Un bug de sensibilité à la casse (comparaison du secret cloud sur `lower` au lieu de `cmd`, même classe de bug que sur le Scénario 09) a été détecté et corrigé avant livraison. Nouvel succès **« Pont Hybride »** dédié à ce chapitre. Ajouté hors-roadmap le 20 juillet 2026 (nouvelles règles `NOISE` pour `dump-adsyncdb`/`decrypt-adsynccreds`, réutilise `dcsyncAny`/`mimikatzGolden`/`connectMguser` existants).
